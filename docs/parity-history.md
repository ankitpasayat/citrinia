**The ship turned up a real hole, fixed as a fourth commit `3c5533b` "Column grants that actually narrow something".** Read this before writing any migration that grants a column:

**`grant update (col) on t to authenticated` narrows NOTHING on Supabase.** The platform ships `alter default privileges in schema public grant all on tables to anon, authenticated, service_role`, so every table is created with `anon=arwdDxtm` and `authenticated=arwdDxtm`. A column grant on top of a table grant is a no-op -- the table grant wins. So the column grants in core, profile and pinned_peel were decoration, and three code comments claiming username was "out of reach" were false. Live consequence, proved by running it as ada in the real stack (`UPDATE 1`): a signed-in reader could PATCH their own profiles row through PostgREST setting `username` -- past `change_username()`, so no `username_history` row (the old handle stopped resolving instead of forwarding), no 30-day hold, no lower-case rule, and a handle `@mention` cannot parse. `created_at` (joined date) was forgeable the same way. On notifications every column was writable and rows could be forged or deleted, with RLS the only thing left. The fix: `revoke all on all tables/sequences in schema public from anon, authenticated`, then re-grant exactly the intended surface.

**Why verify.sql never caught it -- the important part.** `verify.sh` used to revoke the platform's default privileges before applying migrations "so the migration's own grants are what's tested". That made its container the ONE environment where those column grants narrowed anything: strictly more restrictive than production, so it structurally could not catch a grant that was too wide. Checks 6, 12, 28 and 30 were already asserting exactly the right things and had been passing for the wrong reason for weeks. The container now KEEPS the defaults (it asserts they are active), and new check 31 pins the entire anon/authenticated surface -- table grants and updatable columns -- as two literal lists, so a table added by a future migration cannot come in wide open. Both halves were proved red first: a widened grant RLS still blocks (`grant select on follows to anon` -- check 13 stays green, 31 catches it), and an updatable notifications column check 6 never names (`actor_id`).

**Generalise this:** a test environment that is more restrictive than production cannot catch over-permission. When a check asserts "X is not allowed", make sure the container can actually reach the state where X would be allowed.

**The design point worth keeping: `hidden_from` is SECURITY INVOKER, and that is load-bearing three ways.** From `home_timeline` (invoker, as the reader) RLS on mutes is select-own and the answer is truthful. From a notify trigger (definer, so running as owner, past RLS) it answers for ANY viewer -- which a trigger needs, since there the viewer is the *recipient* while the *actor* holds the session. And to somebody fishing (`hidden_from('<alice>','<bob>')`) it answers false, having seen nothing. **A definer version would publish the whole mute graph to anyone with a REST client** -- proved by making it definer and watching check 34 fail with "hidden_from told the muted party they are muted".

**Two shapes of one rule, deliberately.** `blocks_between(a,b)` for a pair (insert checks, hidden_from); `blocked_ids()` for the peels SELECT policy, because it takes no arguments so the planner runs it once and hashes it. Verified, not assumed: `EXPLAIN (analyze)` shows `Filter: (NOT (ANY (user_id = (hashed SubPlan 1).col1)))` with `loops=1`.

**Hiding a row from SELECT does not stop an INSERT naming it by id -- a foreign key check runs past RLS.** So reply, quote, like and repost each needed saying, via `blocked_peel(peel)` which is security definer because answering requires seeing the peel. This is the trap that would have left a blocked person silently inflating your like count.
